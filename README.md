# 数字医疗智慧晨会协同与决策支撑平台

一个平台、五个模块，覆盖晨会全生命周期：从发起晨会、智能签到、实时汇报互动，到问题督办闭环，再到多源数据治理与大屏可视化决策。

## 整体架构

```
                    ┌─────────────────────────────────────┐
                    │  统一前端壳 frontend-shell（:5000）   │
                    │  统一登录 · 统一导航 · 角色化菜单      │
                    └──────────────┬──────────────────────┘
                                   │ ?token= 注入 / API 网关(:8085)
        ┌──────────────┬───────────┼───────────┬──────────────┐
        ▼              ▼           ▼           ▼              ▼
   审批议程        汇报互动      问题督办     数据采集        可视化大屏
   :8082          :8081         :8084       :8083           :8080
```

- **统一前端壳**：登录、导航、账号角色在这里统一处理，五个子系统作为「模块」嵌入，不再各自一个网站。
- **统一后端网关**：`/api/{子系统}/**` 转发到对应后端，认证 JWT 透传。
- **共享数据库**：`smart_meeting`，跨子系统数据走共享表 + RESTful 接口，不直连别人的库。

## 两条业务线

演示和导航都按这两条线走，体现先后顺序：

```
【晨会线】会议管理 → 智能签到 → 汇报互动 → 督办闭环
【数据线】数据采集治理 → 可视化大屏
```

## 现存问题（收尾阶段待解决）

以下是从源码和数据库梳理出的、阻碍整合的问题，需对应负责人解决或确认。

### 1. 账号角色体系不一致（三套并存）

共享表 `sm_gm_members.role` 目前只有两个值：`1` = 管理层（工号 2 开头）、`2` = 普通医护（工号 1 开头）。

| 子系统 | 当前做法 | 问题 |
|--------|---------|------|
| 汇报交互、审批 | 工号 `startsWith('2')` 判断管理员 | 用工号前缀，未用 role 字段 |
| 督办 | 自定义 4 角色 enum（督办专员/执行责任人/参会人/管理员） | 与共享表 role（仅 1/2 两值）对不上 |
| 可视化 | 独立 `sys_user` 表（roleId） | 账号体系与共享表分离 |

**解决方向**：账号角色全局统一为「管理员 / 参会人」两种，从 JWT + 共享表读取；「发起人 / 主持人 / 督办专员 / 执行责任人」是业务流程角色，由会议、任务、分派决定，不作为账号属性。

## 交付要求

### 通用要求（五个都要达标）

1. **统一响应格式**：所有接口返回 `{ success, code, msg, data }`，`success:false` 时 `code` 写错误码、`msg` 写原因。
2. **统一认证**：JWT（secret `smart-morning-meeting-2026`、24 小时过期），从 token 的 `sub` 取工号。JWT 工具类保留，演示阶段拦截器可放通。
3. **统一角色模型**：工号 `2` 开头 = 主持人/管理员，`1` 开头 = 参会人。**不要各自另定义一套管理员判断**，统一从 JWT 读。
4. **跨子系统数据只走「共享表 + RESTful 读接口」**，不直连别人的库。
5. **对外暴露「读」接口**：本子系统产出的数据要能供下游/网关读取（例如汇报交互要提供签到、摘要的读接口给督办和可视化）。
6. **前端可嵌入**：支持 `?token=` 注入登录态，能被 Shell 用 iframe 或微前端加载。
7. **参会人相关功能适配移动端**：签到、互动、汇报查看这些「参会人会用手机」的功能要能在手机端用（或由鸿蒙端覆盖）。

### 各子系统专项要求

**审批与议程管理**（建会）
- 建会时支持**多选参会人员**。
- 产出会议主表 + 议程 + 参会人名单，写入共享表（`sm_meeting_info`、`meeting_agenda`、`meeting_attendee`）。
- 提供「会议详情」读接口，供签到/汇报读取「当前会议」。
- 建会流程要有发起 → 审核 → 发布的环节。

**汇报与实时交互**（过程）
- **自助签到**：登录后一键签自己的到，不需要搜索/输入工号。
- **扫码签到**：二维码 → 手机打开 → 登录 → 自动签到。
- **语音转写**：真实语音识别（已接入 DashScope），方向是「实时转写」，不是手动录入。
- 产出签到、发言、互动、会议摘要，提供读接口。
- 会议质量评分按统一公式实时计算。

**问题督办与闭环**（收尾）
- 问题来源从**晨会摘要/互动中抽取**，不是手动输入。
- 任务分派 → 责任人执行 → 上传进度 → 100% 闭环。
- 消费汇报交互产出的摘要、互动中的「问题/待办」。

**数据采集与治理**（采集）
- 明确**数据范围和维度**：采集哪些医疗数据、哪些字段，清洗后保留哪些维度。
- 清洗、去重、标签化。
- 与晨会数据（签到/发言/质量评分）建立关联，说清「外部数据和晨会数据放在一起的逻辑关系」。
- 产出标准数据表，供可视化读取。

**可视化与决策**（展示）
- 整合多数据源：晨会数据 + 采集治理后的标准数据。
- 不只是展示，支持管理员自助处理/配置数据。
- 消费签到、发言、互动、质量评分 + 标准数据。

## 整合约定（收尾阶段必读）

- **前端**：统一 Shell 承载五个模块，顶部统一导航 + 侧边栏按角色显隐；导航按「晨会线 / 数据线」排。
- **账号权限**：登录留在 Shell，JWT 带工号 + 角色；所有子系统只读 JWT 判断角色，不再各自硬编码。Shell 加「账号/权限管理」页。
- **移动端**：扫码签到 + 参会人相关功能移动端适配。
- **数据流闭环**：审批产会议 → 签到/汇报读会议 → 督办从摘要/互动抽问题 → 可视化整合晨会数据 + 采集数据。

## 从零跑起来

```bash
git clone https://github.com/EternalDust/smart-morning-meeting.git
cd smart-morning-meeting
```

执行你负责子系统的 `sql/init.sql`。不同子系统共用同一个库 `smart_meeting`，如果不是第一个建库的人，跳过 `CREATE DATABASE` 那一行。

```bash

./mvnw spring-boot:run
```

### 3. 前端


## 数据库

**库名**：`smart_meeting`，字符集 `utf8mb4`。

**表名前缀**：`sm_` 晨会业务、`bi_` 大数据分析、`data_` 数据采集治理。

**共享表**（改结构前在群里说）：

| 表 | 用途 | 当前维护者 |
|---|---|---|
| `sm_gm_members` | 人员信息（工号、姓名、部门、角色） | 汪宇涵 |
| `sm_meeting_info` | 晨会主表 | 杨子亨 |
| `meeting_attendee` | 参会人员名单 | 汪宇涵 |
| `meeting_agenda` | 议程表 | 杨子亨 |
| `sm_org` | 组织/科室结构 | 待定 |

业务表各人自己建、自己维护，放进各自的 `sql/init.sql`。

**数据库密码**必须用环境变量，禁止写明文：

```yaml
password: ${DB_PASSWORD}   # 正确
password: 1234             # 错误
```

启动前设 `DB_PASSWORD=你的MySQL密码`（Windows PowerShell：`$env:DB_PASSWORD="你的密码"`）。

## 开发规范

- **包名**：统一 `com.huadi.smm`。
- **目录结构**：`backend/`（controller/service/dao/entity/config）、`frontend/src/`（views/api/router/stores）、`sql/init.sql`。
- **AI 能力**：接口抽象（`AiClient`/`AsrClient`），配了 DashScope API Key 走真实调用，没配走内置实现。API Key 走环境变量 `AI_API_KEY`/`ASR_API_KEY`，禁止写明文。
